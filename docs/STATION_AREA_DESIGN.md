# 駅エリア設計 v1.0

## 1. 対象

Phase Bでは、東京都23区内に中心を持つ駅を「駅エリア」として比較できるようにする。

駅エリアは区の子要素ではなく独立した比較単位とする。区境付近の駅では複数区の250mメッシュを含めてよい。

## 2. 駅エリアの空間定義

- 駅識別子: XKT015のグループコード
- 駅中心: 同一グループコードに属する駅・路線レコードの座標平均
- 比較半径: 1,000m
- 対象メッシュ: 駅中心から1,000m以内に中心点を持つ250mメッシュ
- 対象範囲: 現在の東京23区XKT013メッシュ内
- ID: `station:<group_code>:r1000:v1`
- `definition_version`: `r1000:v1`
- peer group: `tokyo23:station_area:r1000`

`primary_area_id` は駅の代表区を画面表示するためだけに使い、駅エリアの範囲制約には使わない。

## 3. データの意味

駅エリアでは、すべての指標を同じ位置定義へ無理に合わせない。

### 1km圏で集計するデータ

- XKT013 2020人口・2025以降の将来推計人口
- 学校
- 保育園・幼稚園等
- 医療機関
- 図書館
- 公共施設
- 駅・路線・駅別乗降客数

### 駅コード指定で取得するデータ

- XIT001 不動産取引価格情報

XIT001の`station`には、XKT015で利用している駅グループコードを指定する。

この取引データは「駅から1km以内に存在する物件」とは定義しない。「この駅を検索条件として取得できる取引」として扱う。

物件位置を推測して250mメッシュへ割り当てない。

## 4. 駅スコア v0.1

駅スコアは区スコアv0.3とは別の定義・別の母集団で計算する。区と駅の点数を直接比較しない。

| 構成 | 上限 | v0.1の入力 |
|---|---:|---|
| 価格動向 | 20 | 直近5完了年内の駅指定取引の年別㎡単価中央値の変化 |
| 人口動向 | 20 | XKT013 2020人口 → 2025推計人口の変化率 |
| 将来人口 | 20 | 2045推計人口 / 2025推計人口 |
| 生活利便性 | 15 | 1km圏の5施設カテゴリの人口1万人あたり件数を均等合成 |
| 交通利便性 | 15 | 1km圏の人口10万人あたり駅数・路線数・乗降客数/人口を均等合成 |
| 取引活性度 | 10 | 直近5完了年の駅指定取引件数 |

各項目は `tokyo23:station_area:r1000` 内で相対評価する。

### 人口動向の注意

駅1km圏の2025年国勢調査実績値は現在のプロジェクトに未導入のため、駅スコアv0.1ではXKT013の2020年人口から2025年推計人口への変化を暫定利用する。

画面では必ず「人口動向（推計）」または同等の表現を使い、2025年実績と誤認させない。

将来、細粒度の2025年実績人口を導入した場合は `station-v0.2` など別スコアバージョンへ更新する。

## 5. 総合点の適格条件

次をすべて満たす駅だけ総合100点を表示する。

- 6構成項目がすべて算出可能
- 直近5完了年の駅指定取引が30件以上
- 価格指標に利用できる年が3年以上
- 2020・2025・2045人口が取得可能
- 2020人口と2025人口が0より大きい
- 1km圏250mメッシュが1件以上

条件未達でも算出可能な構成点は表示する。欠損を0点にしない。

### 駅信頼度 v0.1

- A: 6項目完備、取引100件以上、価格5年以上
- B: 充足率95%以上、取引50件以上、価格4年以上
- C: 充足率80%以上、取引30件以上、価格3年以上
- D: それ未満

区の信頼度基準とは別物である。

## 6. DB

Phase Aのテーブルを利用する。

- `geo_units`: 駅エリア本体
- `geo_unit_meshes`: 駅1km圏と250mメッシュの対応
- `geo_metrics`: 駅指標
- `geo_scores`: 駅スコア

駅指定XIT001の正規化済み行は `station_transactions` に保存する。

```sql
CREATE TABLE station_transactions (
    station_group_code TEXT NOT NULL,
    transaction_id TEXT NOT NULL,
    year INTEGER NOT NULL,
    quarter INTEGER,
    transaction_date TEXT,
    municipality_code TEXT,
    district_name TEXT,
    price_category TEXT,
    property_type TEXT,
    total_price REAL,
    unit_price REAL,
    area_sqm REAL,
    source_id INTEGER,
    PRIMARY KEY (station_group_code, transaction_id)
);
```

駅取引は空間座標を持たせない。

## 7. バージョン

- 駅エリア定義: `r1000:v1`
- 指標: `station-metrics-v0.1`
- スコア: `station-v0.1`
- peer group: `tokyo23:station_area:r1000`

半径を500mへ変更する場合、同じIDを上書きしない。

## 8. 公開JSON

```text
web/data/geo/index.json
web/data/geo/station/<group_code>.json
web/data/rankings/station.json
```

Windowsでのローカル開発を考慮し、ファイル名には`station:<code>:...`のようなコロン入りgeo_idを使わず、6桁グループコードを使用する。

## 9. UI

`stations.html` を駅比較専用画面とする。

- 駅検索
- 駅ランキング
- 指標切替
- 2駅比較
- 駅詳細
- 集計定義の説明

駅詳細では、価格・取引の集計定義と1km圏集計の定義が異なることを明記する。

## 10. 更新パイプライン

```text
XKT013取得
  ↓
geo foundation同期
  ↓
施設・XKT015取得
  ↓
1km駅エリア生成
  ↓
XIT001を駅グループコードで取得
  ↓
駅指標計算
  ↓
駅スコア適格性判定
  ↓
駅peer group内で相対採点
  ↓
静的JSON生成
  ↓
GitHub Pages
```

駅指定XIT001はAPIリクエスト数が多いため、当年途中の取得を標準では行わず、完了年までを対象にする。

## 11. Phase B完成条件

- XKT015グループコード単位で駅が重複しない
- 駅1km圏が区境をまたげる
- 250mメッシュ中心距離で範囲が再現可能
- 駅指定XIT001を位置データとして誤用しない
- 駅だけのpeer groupで採点する
- 不適格駅は総合点を出さない
- 個別指標は欠損を0点にしない
- 駅ランキング・2駅比較・詳細表示が静的サイトで動く
- 既存23区ページと区スコアを壊さない
